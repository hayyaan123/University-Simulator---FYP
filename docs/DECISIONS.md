# Decision log

A short record of key technical decisions and why we made them. Add new decisions to the top.

| # | Decision | Why | Alternatives considered |
| --- | --- | --- | --- |
| 17 | Parameters are set once, before a run starts, and the simulation then plays out. To try other settings, change them and press Reset for a new run. This replaces the part of #7 about changing parameters while the sim runs. Path closures stay live, because they are a control, not a parameter (2026-10-01, team) | Every semester of a run has the same settings, so two runs can be compared fairly and the same seed always gives the same result. It is also how the code already works, so nothing extra has to be built | Changes applied from the next semester; changes applied live, mid-semester |
| 16 | Group `sim/` into subfolders by what the code models (`core`, `campus`, `timetable`, `students`, and later `errands`, `staff`, `logging`) | About ten new files are planned for `sim/`. Grouping gives each area one owner and each new file an obvious home. Done while there were only nine files and no open pull requests | Keep `sim/` flat |
| 15 | Call the project "Campus Simulator" in docs and presentations (2026-10-01, our supervisor's suggestion). The map data is still the OpenStreetMap extract of Monash University Malaysia | Avoids presenting the project as an official university product | Keep "University Simulator 2026" |
| 14 | Use knapsack for errands in free time, for fitting classes into rooms and for fitting units into a workload limit; TSP for the order of errand stops; Dijkstra for walking routes (2026-10-01, confirmed with our supervisor) | Each algorithm solves a real problem in the sim, so it can be shown working and explained | Knapsack for errands only |
| 13 | Low energy or high stress can make a student skip a class or leave early (2026-10-01, team) | Something has to cause skipping now that Base attendance chance is gone. The states change a choice; they still never appear in each other's formulas | A set skip probability |
| 12 | Grades, stress, energy and satisfaction are driven separately by determinants (what students do and experience), never by each other. Nothing changes grades directly: a determinant only changes the hours a student puts in, and assessments measure the result (2026-10-01, our supervisor's feedback) | Calculating one state from another is too simple. With shared determinants, the trade-off between the metrics comes out of the model: attending raises grades and stress and lowers energy | Grades calculated from energy and stress; a grade bonus per assessment completed; a grade penalty for arriving late |
| 11 | Grades are Must have, and the end-of-semester metrics are the averages of the four student states (2026-10-01, our supervisor's feedback) | It's a university sim, so grades are the obvious measure of success. Several metrics that trade off stop one setup from being "best" | Grades as Good to have; dashboard stats only |
| 10 | Cut v1 to the 15 parameters in `docs/PARAMETERS.md`: 11 Must and 4 Good. This replaces #9. Staff (#8) moves to Good to have, Semester 2 | Our supervisor's advice on 2026-10-01 was that about 15 is plenty for a first version and each one needs a justification. Every kept parameter reaches a metric through the determinants table. Lecturers are Good to have on the first-meeting whiteboard | Keep the 44 |
| 9 | Fix the parameter list at the 44 in `docs/PARAMETERS.md`. On 2026-09-29 our supervisor agreed we stop at 46; the team then removed Motivation (average) and Burnout threshold, which became fixed values in the code | Enough to cover the what-if questions; more would make results hard to explain and every default needs a source. Motivation and Burnout threshold were hard to source and overlapped with Base attendance chance and Resilience | Keep adding parameters; the ones in "Considered and dropped" |
| 8 | Simulate lecturers and tutors as agents with their own timetables, not only students | Staff clashes and teaching limits make the timetabling problem realistic; a teacher walking between classes makes classes start late; staff absence causes cancellations. Few agents, so it costs little | Students only, with classes always starting on time |
| 7 | The simulation runs continuously, semester after semester, until the user stops it. Stats are reported at the end of each semester | It's a what-if tool with no end-game. Long-run effects (stress building up, dropouts, cohorts moving through years) only show up over many semesters, and users can change parameters and watch the next semesters respond | Fixed-length runs (one week or one semester) that end, then Reset |
| 6 | GitHub repo with Issues + Project board | Repo already set up; Issues/board give us task tracking and evidence of project management | GitLab |
| 5 | Semester 2 ML: small models run in GDScript from JSON first; Python sidecar only if time allows | No plugins, works on every machine, fast, easy to explain. The planned models (logistic regression, trees) are simple to evaluate by hand | Python sidecar only; GDExtension ONNX plugin (community-maintained, harder setup) |
| 4 | Many small models, one per decision | Easier to train, test and explain than one large model | One combined model |
| 3 | Discrete-event simulation with continuous time | Travel time and lateness need minute-level precision; faster than ticking every agent every frame | Fixed time-step agent loop |
| 2 | GDScript (Godot Standard build) | Simple setup for the whole team; no .NET needed | C# (.NET build) |
| 1 | Godot 4.7 | Supervisor's suggestion; lightweight, open source, good 2D tools | Unity |

Hand-set probabilities are used until the ML stage. Real datasets (OULAD, UCI) are only needed for training in Semester 2.
